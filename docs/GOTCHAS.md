# GOTCHAS.md

Known mistakes and their fixes. Read the section for your area before starting work, and add new entries under the matching heading as `- [YYYY-MM-DD] Symptom → Correct approach`.

An entry names the trap in bold, then gives the symptom as it actually appeared, then the fix. A section with no entries says so; do not invent one to fill it.

The entries below were carried over from the owner's previous Rust project on
this same machine and toolchain. They are kept because they are true of this
Windows box, this GPG setup, this Forgejo runner and the Rust edition in use,
and because re-learning any of them costs hours. The project-level entries from
that codebase were dropped — nothing here refers to code OmniToaster does not
have.

## Git, Merges and Releases
- **`origin` has no fetch refspec, so `git fetch origin` refreshes nothing.** `remote.origin.fetch` is unset in this checkout: `origin/main` only moves when *you* push to it, never when the release workflow commits on `main`. A branch cut from `origin/main` after a release was based on the previous release's commit and built without the work merged in between. Before branching or merging, fetch with the refspec spelled out - `git fetch origin +refs/heads/main:refs/remotes/origin/main` - or compare against the forge's `branches/main` API.
- **A merge resolution and its commit must be one `&&` chain, and the marker count a hard gate inside it.** A resolution script died on a `/tmp` path, the `;` after it let `git add && git commit && git push` run anyway, and a merge with `<<<<<<<` in `CHANGELOG.md` reached `main`. The shape that cannot do this is `resolve && test "$(grep -c '^<<<<<<<\|^=======\|^>>>>>>>' CHANGELOG.md)" = 0 && git commit …` - every step a gate, nothing after a `;`.
- **Never read a push's result through `| grep -v remote | tail -1`.** A push is a gate: check its exit code (`git push … || echo PUSH FAILED`) and `git log -1 origin/main` after it, exactly as a `cargo` gate is checked by its exit code and not by eye.
- **Commit gates must check exit codes.** `cargo clippy ... | grep ... ; git commit` committed code with lint errors. Use `cargo clippy ... >/dev/null 2>&1 && git commit`, not a check on printed output.
- **Never use `--no-verify` or `--no-gpg-sign`.** If GPG signing fails, fix the agent (see the gpg-agent note below). Don't bypass it.
- **gpg-agent cache.** `%APPDATA%\gnupg\gpg-agent.conf` sets `default-cache-ttl 14400`. The agent re-reads it only after `gpgconf --reload gpg-agent`. `gpgconf --kill gpg-agent` drops the cache.
- **Two GnuPG installations share one `~/.gnupg` here.** `gpg` on the Git Bash PATH is MSYS GnuPG 2.4.5 and cannot read the keyboxd `pubring.db` that `common.conf`'s `use-keyboxd` selects: it reports `skipped "<key>": No secret key` and lists no keys at all, which looks like a lost key and is not. Only `C:\Program Files\GnuPG\bin\gpg.exe` (2.5.16) sees them, and it is what `gpg.program` points git at. Probe signing with that full path, never the bare `gpg`. The harmless-looking `sending fd … to keyboxd: Input/output error` it prints is not the failure; read the `[GNUPG:]` status lines for `SIG_CREATED` or `Timeout`.
- **CHANGELOG conflict markers.** A merge of a release into a feature branch left `<<<<<<<`, `=======`, and `>>>>>>>` in `CHANGELOG.md` for five releases, and nothing caught it. Run `grep -n '^<<<<<<<\|^=======\|^>>>>>>>' CHANGELOG.md` before any merge commit. CI fails on markers in tracked text.
- **Resolving a CHANGELOG conflict.** Never keep "both". The released section belongs to the release workflow, so keep its generated text as is. Unreleased keeps only items not yet released. Confirm with `grep -c '^<<<<<<<\|^=======\|^>>>>>>>' CHANGELOG.md` (must print `0`).
- **Writing Unreleased notes before a release lands** guarantees that conflict. Expect it, and resolve it as above.
- **New workspace member on a branch + merged release bump.** The version script can't see a crate that exists only on the branch, so `Cargo.lock` keeps its old version and every `--locked` command fails with "cannot update the lock file". Run a plain `cargo check`, then commit the one-line lock fix. The release job may already have tagged `main`.
- **Diff base.** `git diff <base>..HEAD` for "the last N days" needs the right base commit. A wrong base produced empty diffs for six crates in review.

## Release Pipeline and Updater
- **CI must pass `-j 4` like everything else on this machine.** The Forgejo runner *is* the owner's Windows box, so an unbounded `cargo test --workspace` there exhausts the paging file exactly as it does from a shell: a run died with `rustc-LLVM ERROR: out of memory` / `STATUS_ILLEGAL_INSTRUCTION` compiling one crate's lib test, on a commit that changed only Markdown and PNGs. The rules have mandated `-j 4` for local work all along; the Forgejo workflows must too. The `.github/` copies are deliberately left unbounded - those run on GitHub-hosted machines.
- **The "nothing to release yet" guard stops protecting you the moment `Cargo.toml` exists.** `release.yml`'s plan step short-circuits on `if (-not (Test-Path Cargo.toml))` and emits an empty version, which skips every later step - so while Phase 0 was unstarted, documentation pushes to `main` stayed green and published nothing. The commit that created the workspace removed that protection in the same breath: with a `Cargo.toml` present and a `feat:` commit in history the planner computed a minor bump and the job walked on into signing, which threw on the unset `OT_MINISIGN_KEY`. Nothing was damaged, because the version bump and tag are local until a step *after* signing pushes them - confirm with `git ls-remote --tags` and the releases API rather than assuming. The lesson for the ordering: keep publish-affecting steps after everything that can fail, and have the signing key and `keys/minisign.pub` in place **before** the first `feat:` reaches `main`, or every push re-attempts the same version and fails.
- **The forge intermittently stops creating workflow runs, and it is not always loud about it.** Seen three times in one day (BUG-0001). The first came with `502 Bad Gateway` in the runner's task fetch; the next two came with a completely clean diagnostic — forge answering `/api/v1/version`, `gitea-runner` service Running, no error in its log, the commit confirmed on the remote with `git ls-remote` — and still no run row. A silent stall and a 502 are the same fault wearing different clothes, so the absence of an error proves nothing. Don't start editing the workflow: it worked an hour ago and it will work again. `ci.yml` carries `workflow_dispatch` for exactly this, which needs the forge UI or an authenticated call.
- **A push that creates no workflow run at all is usually the forge, not your `on:` filter.** A branch pushed at 05:26 reached Forgejo - `git ls-remote` showed the commit on `refs/heads/<branch>` - but `/actions/tasks` still reported `total_count` 1 twenty minutes later. The `on.push` filter looked guilty (`branches: ['**', '!main', '!beta']` uses `!` negation, which not every Forgejo version honours), and it was innocent: the next branch push triggered `ci.yml` within seconds with the filter untouched. The runner log is what settles it - `C:\Apps\gitea-runner\service-err.log` had `fetching a task timed out after 5s` and `failed to fetch task: unavailable: 502 Bad Gateway` in exactly that window. Check three things before editing a workflow: the commit really is on the remote, the runner log for fetch errors, and `/api/v1/version` for the forge itself. A `000` from `curl` against the forge means the probe failed, not that the forge is down - repeated rapid probes get rate-limited by the proxy in front of it, while `git` over the same host keeps working.
- **An out-of-memory CI failure looks like a code failure.** It is reported as `could not compile <crate>`, and the crate named is simply whichever one was unlucky, not the one at fault. Before debugging the code, check whether anything else was running on the machine - a GUI app, a screenshot harness, another cargo - and re-run on a quiet machine.
- **A red release run after the publish step is a verification failure, not a failed release.** The release is live by then; the step that follows downloads it and runs the exe's `--self-test` *on the runner*, as LocalSystem in session 0, where a GUI or terminal probe can trip on things that work fine on the desktop. Re-verify the downloaded asset from the desktop before treating the release as broken. Flush each self-test line as it prints, give any probe a second and longer try, and turn a panic inside a check into a `FAILED` line - so a red verify names its reason instead of just stopping.
- **Back-filling releases in ascending order leaves the wrong one flagged "Latest".** GitHub marks the most recently *published* non-prerelease as latest, not the highest version. Publishing v0.1.0 through v0.4.0 after v0.4.1 already existed left `/releases/latest` answering **v0.4.0**, which would offer a v0.4.1 user a downgrade. Fix with `gh release edit <newest> --latest`, and expect the API to serve the old answer for a few seconds afterwards while the listing already shows the new one. Back-filling newest-first avoids it entirely.
- **A pipeline step that "skips when unconfigured" and exits 0 is indistinguishable from one that works.** `scripts/push-to-mirror.ps1` prints "GitHub mirror not configured … skipping" and exits 0, so the release job goes green having mirrored nothing. Three releases shipped to Forgejo with GitHub getting **no tags and no releases** before anyone asked. The trap is sharpened by `origin` carrying GitHub as a second **push url**: `git push origin main` reaches both forges, so `main` looks perfectly current on the mirror while tags — which only the skipped step pushes — never arrive. When adding a "configured?" guard, make the skip visible in the run summary, and consider making it an error once the thing has been configured once, because from then on a skip means a break rather than a choice.
- **Tag and mirror.** The release job's last step fast-forwards GitHub to the version commit (never forced), pushes the tag, and dispatches GitHub's workflow. Never set a Forgejo push mirror while GitHub is writable.
- **Changes made on GitHub** come back with the sync script (fast-forward only).
- **Every GitHub job** is guarded with `if: github.server_url == 'https://github.com'`. Forgejo Actions also reads `.github/workflows/` and can't fetch published actions.
- **A subject on a merge commit never reaches the release notes.** `scripts/next-release.ps1` builds them with `git log --no-merges`, which is right — merge subjects are noise — and means a substantive change carried *on* a merge commit is invisible. Resolving a conflicted `git merge` and committing produces a merge commit, so a `fix:` subject written there is dropped: the bump-table correction and the `style:` lesson in `1803d64` are absent from v0.3.0's notes for exactly this reason. Keep a merge commit a plain merge and put the substance in its own commit before or after it.
- **Writing long hand-written entries under `## Unreleased` is wasted work.** The release workflow replaces that whole section with one line per commit subject, generated. Mine were discarded three times across v0.1.0, v0.2.0 and v0.3.0 before the penny dropped. The rules already say one line per change; the detail belongs in the commit message and in `TASKS.md`, both of which survive. Write the one line, and only for things a commit subject would not already say.
- **The commit type decides whether a change ships *and* whether anyone is told about it.** `docs`, `chore`, `refactor`, `test`, `ci`, `style` and `build` are in `$NoReleaseTypes` in `scripts/next-release.ps1`: no version bump, and **no line in the release notes at all**. That is correct for real no-ops and wrong the instant such a commit changes something a user sees, because it then ships silently on the back of whatever releasable commit shares the push. CR-0001 renamed the product in every visible string under a `style:` subject and shipped in v0.2.0 with no mention in v0.2.0's notes; released sections are never hand-edited, so that cannot be fixed afterwards. A change to user-visible text is `fix:` or `feat:` no matter how cosmetic the diff looks.
- **A `version` on a `path` dependency breaks the first *minor* release and nothing before it.** `crates/omnitoaster/Cargo.toml` carried `ot-platform = { version = "0.4.0", path = "../ot-platform" }` while the version lives once in `[workspace.package]` (ADR-001). `scripts/update-version.ps1` moved the workspace to 0.5.0; the pin kept its literal, and the release's `cargo build` died with `failed to select a version for the requirement ot-platform = "^0.4.0"` — candidate 0.5.0. It survived v0.1.0 to v0.4.1 because a caret requirement accepts every patch bump, so the trap springs on a minor release, whose change has nothing to do with manifests. It also surfaces *inside* `scripts/build-and-package.ps1`, which makes it look like a packaging fault; the script is only reporting `cargo`'s exit code, and the mangled `. XITCODE -ne 0) { … }` in its error output is PowerShell's rendering, not a broken line. `crates/omnitoaster/tests/manifests.rs` now fails the gate on any dependency line carrying both a `path` and a `version` (BUG-0003).
- **Release notes** are generated from commit subjects. Hand-edit only the Unreleased section.

## Patch Scripts and Text Editing
- **`grep -c` the markers after any re-run.** Checking "new text present" isn't enough when the new text starts with the old text. Make each patch step idempotent, and test for a marker that exists only *after* that step - re-running a half-applied patch has duplicated whole functions.
- **Unicode escapes in Python.** `\u{b7}` or `\u{2192}` in a Python string is an error ("truncated \uXXXX escape"). Put the character itself in the text, or build it with `chr()`. Doubling the backslash writes a literal `\\u` into Rust, which compiles to the wrong thing. This bites when the *Rust* you are generating contains the escape too: a patch script adding `text.replace(['\u{2068}', '\u{2069}'], "")` died before running a line. Use the editing tool for text containing Unicode escapes rather than scripting it.
- **Windows paths in Python.** Use raw strings (`r"C:\Users\..."`). `"C:\Users"` fails on `\U`.
- **Windows paths in TOML.** Use single-quoted literal strings (`audio_path = 'C:\Users\...'`). A double-quoted TOML string processes `\U`, and an invalid escape fails the whole file. The symptom was only a "TOML parse error" and a setting that never appeared.
- **It is not only heredocs — any double-quoted shell string eats backticks.** This entry said "heredoc" for months and that wording is exactly why it failed to stop me: `python -c "...markdown with \`backticks\`..."` is a double-quoted string, so bash ran each backtick span as a command and substituted the empty output. Two CHANGELOG and CHECKLIST lines landed with their code spans silently blanked — `- The app icon:  as the master, seven generated sizes and a  embedded into  with...` — and the script still printed "updated". The rule is about the **shell**, not the heredoc: single-quote the string, or use the editing tool, which is what the next bullet already says and what should simply be done for anything containing backticks or `$`.
- **Heredocs.** Use `<<'EOF'` (quoted). An unquoted heredoc expands `` `backticks` `` (blanking names in doc comments) and `$name` (turning Fluent text into `Remove { }?`, a parse error that dropped the whole message). Better still, write the script to a file with the Write tool and run it.
- **Quoting accidents.** Two lost patches came from quoting, not logic. Write scripts to files.
- **Python on Windows writes CRLF.** `open(p, 'w')` translates `\n` to `\r\n`, so a patched LF file comes back with every line changed (git warns "CRLF will be replaced by LF"). Open with `newline=''` for reading and writing. Fix a damaged file with `sed -i 's/\r$//'`.
- **After a release, CHANGELOG's Unreleased has no subheadings.** The release commit resets it to `- (nothing yet)`, so a script that finds `### Fixed` (or any heading) by searching forward from `## Unreleased` lands in the version just released and files the line under it. Bound the search at the next `## ` heading, and replace the placeholder when it is there.
- **The Bash tool can refuse a long heredoc** ("unexpected EOF while looking for matching `'`") even when quoted, depending on the text. Nothing in it ran. Write the script to a file with the Write tool and run the file.

## Storage and Migrations
- **`fs::canonicalize` on Windows returns a `\\?\` path, and it leaks.** Resolving the data root through `canonicalize` is right - it removes `.` and `..` so later `starts_with` comparisons mean something - but the result comes back as `\\?\D:\…`, the extended-length form. It then reaches the user in log lines and error messages, and reaches other programs as an argument many of them reject. Strip the prefix for anything stored, shown or passed on (`\\?\UNC\server\share` is the verbatim form of `\\server\share`), but **keep it when the path is at or past the classic 260-character limit**, where the prefix is what makes the path work at all. `ot_core::paths::strip_verbatim_prefix` does this; the symptom if you skip it is a startup line reading `Data folder: \\?\D:\…`.
- **Stripping the `\\?\` prefix breaks every `starts_with` check against a canonicalized path.** Having removed the prefix from the stored data root, the containment check in `DataRoot::join` compared a freshly canonicalized `\\?\D:\…\logs` against a stripped `D:\…` root, `starts_with` was false, and `join` refused **every path inside the root that already existed** — which meant logging could not start at all. Strip both sides, or neither. The failure was invisible to the test that existed, because it only joined a path that did *not* exist and so never reached the canonicalize branch: a success test for a non-existent path does not cover the existing-path case.
- **Prove a folder is writable by writing to it, not by reading its permissions.** A permission check still says yes on a full disk, a read-only mount, or a folder an ACL denies in a way the simple check misses. Write a probe file and delete it - and make sure the probe is deleted on the success path, or the data folder gains a stray file on every start.

## Windows Environment and Build
- **The CI runner is a service running as LocalSystem, whose HKCU is not a user's.** `gitea-runner` runs as `LocalSystem`, so `HKEY_CURRENT_USER` resolves to the `S-1-5-18` profile under `C:\Windows\System32\config\systemprofile`. That profile has `Software\Microsoft\Windows\CurrentVersion` but **no `Run` subkey**, so registry code that assumes the Run key exists works on every developer account and fails only on CI. Check with `Test-Path "Registry::HKEY_USERS\S-1-5-18\Software\Microsoft\Windows\CurrentVersion\Run"`. The same mismatch is why a GUI or terminal probe behaves differently there, which this file already records for `--self-test`. Treat a missing key as "nothing is set" rather than an error, and create it on write.

- **Disk filled by `target/debug`.** Delete `target/debug/incremental` (cache only; `debug/deps` stays, and the next build isn't a full rebuild). Check after long sessions. Check free space *first* when a build misbehaves - a full disk does not announce itself, it shows up as `LNK1140: limit exceeded for program database` (the linker cannot write the PDB).
- **`LNK1140: limit exceeded for program database`.** The PDB outgrew its format limit. No code change causes or fixes it. Don't set `CARGO_PROFILE_DEV_DEBUG=0` on the command line. That changes every fingerprint, rebuilds the whole workspace, and fills drive space. If it recurs, set the debug level in `Cargo.toml` so the fingerprint is stable.
- **Paging file exhaustion.** `cargo test --workspace` can fail with "the paging file is too small" (os error 1455), then "found invalid metadata files for crate …" on every later run. The parallel build exhausts the commit limit, not RAM. Delete `target/debug` and use `-j 4`. A rustc killed mid-write leaves corrupt `.rmeta`/`.rlib` files.
- **Two cargo invocations on one target folder** serialise on the build lock.
- **A background `cargo test` started before a new crate is registered** fails on the missing module. Re-run after registering.
- **Release build fails with "Access is denied".** A running `OmniToaster.exe` keeps its own file locked. Run `Stop-Process -Name OmniToaster -Force` before `cargo build --release`. During development, always use `--data-dir ./tmp-data` so the real `OmniToasterData/` is never touched.
- **PowerShell variable names ignore case, and a load script on this machine loads the CI runner too.** A reproduction script took `-Hogs 32` and stored the started processes in `$hogs` — the same variable — so the assignment failed, the cleanup had nothing to stop, and 32 busy loops ran on for over an hour, stretching a two-minute CI run past thirty-five. Give such a variable a different name, and after any load test check `Get-Process` for what it left behind before reading a slow CI run as a CI problem.

## Build and Dependency Gotchas (Rust)
- **CI runs `cargo deny check`, and its result does not depend on the branch.** Advisories come from the RustSec database and that moves on its own, so a branch whose `fmt`, `clippy`, tests and `--self-test` all passed yesterday can go red today with no change of its own. Run `cargo deny check` as part of the gate, and before a push if the branch has been open a while. The fix is usually `cargo update -p <crate>` for a patch bump - but check whether the code actually reaches the vulnerable path and say so either way, rather than implying a vulnerability shipped. The other CI step the local gate skips is the release build plus `--version` / `--self-test` on the exe.
- **Setting `[workspace.package] version` *back* to one already built leaves a stale exe.** Cargo rebuilds when the version moves forward, but on the way back the artifact for that version is already in `target/debug/deps`, cargo reports "Finished" without recompiling, and the uplifted `target/debug/OmniToaster.exe` keeps pointing at the other version's binary — so `--version` prints the version you just left and `version_prints_the_one_word_product_name` fails against a manifest that is perfectly correct. Hit while simulating a 0.5.0 bump to prove BUG-0003's fix. `touch crates/omnitoaster/src/main.rs` and rebuild. It cannot reach a release, which only ever moves the version forward.
- **Edition 2024 reserved keyword.** `gen` fails to parse ("expected identifier, found reserved keyword"), which broke 18 places from one field. Name it `generate`.
- **Items after a test module.** Appending functions to a file puts them after `#[cfg(test)] mod tests`, which clippy refuses ("items after a test module"). Insert before the test module. `cat >>` is safe only for files without one.
- **A test must never open a window.** CI runs as a service in session 0, where no window can open at all, and a test that blocks on one hangs the run rather than failing it — the run is eventually *cancelled*, which is not a red test with a name on it. When `--worker` started opening the settings window, every `tests/cli.rs` case that runs the exe had to keep a flag that short-circuits before it (`--hold-ms`). Check **every** `Command::new(exe())` in the file, not just the obvious one: the case that bit was the *third* instance inside `a_second_instance_bows_out_instead_of_starting`, which exists to prove the guard is released and had no flag because it never needed one before. The window is checked in the running app instead, and the ledger item says so rather than ticking a box no test covers.
- **A running app makes `cargo test` test the previous build, and it reports green.** Cargo uplifts the binary to `target/debug/<name>.exe` for `CARGO_BIN_EXE_*`; a running copy locks that file, cargo cannot replace it, and the integration tests then run **the old exe** while the summary looks perfectly normal. This is how a gate run reported 110 passing while the suite in fact hung on CI. The error is visible — `failed to remove file ... Access is denied (os error 5)` — but it is one line in a build log that otherwise says nothing is wrong. `Stop-Process -Name OmniToaster -Force` before testing, and treat any "Access is denied" from cargo as "the results you are about to read are from the last build". Running the suite under a timeout (`timeout 900 cargo test …`) turns a hang into a non-zero exit instead of a number that cannot be trusted.
- **A dependency's default features can fail `cargo deny` on a licence, not a version.** Adding `egui` red-lit the licence pass: its default `default_fonts` feature pulls `epaint_default_fonts`, which ships the Ubuntu font under `OFL-1.1 AND Ubuntu-font-1.0`, neither on the allow list. The fix was `default-features = false` (ADR-014), not an allow-list entry — the app does not want a bundled Ubuntu font anyway. Check what a new dependency's default features drag in before reaching for `exceptions`. The same crate also brought the unmaintained `ttf-parser` through `ab_glyph`, which needed an `ignore` entry whose reason says why the code cannot reach untrusted input.

## Clippy and Lints
- **Don't let lints pile up.** Fix them, or use a scoped `#[allow(...)]` with a reason. Never a crate-wide allow.
- **Clippy must pass with `-D warnings`** on every crate, including Linux. Only `ot-platform` may hold Windows-only code; a platform dependency anywhere else breaks the Linux run.

## egui and Toast Rendering
- **`ViewportBuilder::with_taskbar(false)` does not keep a window out of Alt+Tab.** It removes the taskbar *button* through the shell's taskbar list and leaves the extended style alone, so the window keeps `WS_EX_APPWINDOW`, never gains `WS_EX_TOOLWINDOW`, and still appears in Alt+Tab. Alt+Tab membership is decided by that style, so the style is what has to change — `ot_platform::toast_window` sets it on the real window after it exists. Read the flags back from Win32 rather than trusting the builder: `GetWindowLongPtrW(hwnd, GWL_EXSTYLE)` is one call and it is the only thing that settles it.
- **A deferred viewport whose owner stops asking for it does not close by itself.** egui keeps it alive until something tells it to go, so a retired toast leaves an empty window on screen. Send `ViewportCommand::Close` to its id when it retires.
- **With `default_fonts` off, `FontDefinitions::default()` is empty and all text measures zero.** A layout test then passes without laying anything out: nothing wraps, nothing overflows, every width assertion holds. It looks green and proves nothing. A test that measures text has to install a real font — `ot_platform::ui_font::proportional()` — and is worth guarding with one assertion that the font measures something, so the mistake cannot return quietly.
- **`TextWrapping::break_anywhere` is not the fix for an unbreakable word.** It applies to all text, so ordinary prose breaks mid-word — "with your curren / t settings" — which reads as a rendering fault. egui already breaks a word that cannot fit a line of its own, so leave it off and both cases are handled.
- **egui has no font fallback beyond what you load, so a glyph the tray draws can be `?` in the window.** Windows silently falls back to Segoe UI Symbol for a menu, which is why the tray's bell worked; egui does not, so the same bell on a button drew as `?`. Load `seguisym.ttf` last in both families — it then only answers for glyphs the UI font lacks. Look at every glyph on screen: a codepoint existing somewhere on the system is not the same as it drawing here.
- **An automation click can land on a control that has scrolled under the pointer.** Twice, a click meant to move the pointer over a scrolled pane changed a setting — once the Opacity slider, once a preset on the map — and the second looked exactly like the app choosing a position by itself. When a setting changes that nobody chose, rerun the sequence on a fresh process and check the file after each step before suspecting the app.
- **`DynamicImage::thumbnail` scales *up* as well as down.** It fits the image to the box, so a 16 px icon came back 64 px — four times the memory and blurred. Only call it when the image is larger than the bound.
- **A frame you can only find zoomed in is not a frame.** The image border was first drawn in the toast's border colour, `#3a3a42` on `#26262c`: present at 300%, invisible at 100%, so turning the option on changed nothing anyone would notice. Check contrast at the size people will see, not in a sampled pixel.
- **Scripting the Windows Open dialog is unreliable, and it fails by choosing a *different* file.** The first dialog a process opens can lose the typed keystrokes, and Enter or Alt+O then opens whatever the dialog had preselected in its remembered folder — twice that was a 1024 × 1024 picture nobody chose. Autocomplete can do the same on the name box. The import's content hash proves what was actually imported; check it against the file you meant before believing a screenshot.
- **Never compute a click from a process's `MainWindowHandle`.** Once a dialog has been open, the "main" window can be another one, and a click from the wrong rect lands wherever that is. Find the window by its title.
- **`Color32` stores premultiplied alpha.** Reading a channel back after `from_rgba_unmultiplied` gives the premultiplied value, not the one that went in: `0x3b` at 40% opacity reads as `24`. Right for painting, misleading to inspect — assert against the colour egui itself would build rather than against `.r()`, `.g()`, `.b()`.
- **A corner radius larger than half a rect's shorter side draws nothing useful.** A 4 px accent bar given the toast's own 12 px radius is a degenerate shape; clamp the radius to what the rect can hold.
- **Check a toast within its own lifetime.** A default toast lasts eight seconds; a screenshot taken a moment too late shows an empty desktop and looks like a window that never opened. The first run of this check went looking for a bug that was not there.
- **egui grows widgets under the pointer by default.** `Visuals::widgets.*.expansion` is non-zero out of the box, so a button nudges bigger on hover — which the UI rules forbid outright. `ot_ui::theme` zeroes `expansion` on all five widget states, and `hover_never_grows_a_widget` asserts it, because it is the kind of thing only a human notices on screen. Any scope that resets the style to egui's default brings it back.
- **`egui::Stroke::new(1.0, colour)` does not compile.** The width is generic over `Into<f32>`, so a bare `1.0` has no type to infer and the compiler reports a `f32: From<f64>` bound failure rather than the real problem. Write `1.0_f32`.
- **`add_sized` centres what it is given, so a label in a sized box floats in the middle of its own column.** The fix is `allocate_ui_with_layout` with `Layout::left_to_right(Align::Center)` — left-aligned horizontally, centred on the field's middle line vertically, which is what the rules actually ask for.
- **A label column shrinks to its text unless you set `min_width` inside it.** Every row then starts its field at a different x and the form reads as a ragged edge instead of a column. Work the split out **once per pane** (`ot_ui::layout::columns`) and pass it to every row, rather than recomputing it per row from that row's own width.
- **`horizontal_wrapped` wraps against the pane, not against the column you indented into.** A long hint starts its second line under the label, where it reads as a different paragraph. Put the hint in an `allocate_ui_with_layout` of the field's width with `set_max_width`. Malay runs up to 30% wider than English, so this is the normal case there, not an edge case — it is invisible in English.
- **A narrow window has to move the label above the field, not shrink the field.** Clamping a field to a minimum width inside a row that no longer has room pushes it straight off the pane: the field is drawn, clipped, with its dropdown arrow outside the window. Decide between side-by-side and stacked from the width the pane actually has.
- **Windows 11 hides a new tray icon in the overflow, so "the tray does not work" usually means "the icon is behind the chevron".** It is the user's to drag onto the taskbar and the app must not fiddle with that, but it means a first run looks like nothing happened. It also makes the tray hard to verify from a session that can only drive the mouse: the chevron has no findable position, the notification area is a XAML island that exposes nothing through UI Automation, and Win+B does not open the flyout. Check the icon's *creation* (a failure is reported in the status line) and leave clicking it to someone at the machine.
- **A hidden eframe window keeps being updated, but Windows throttles it.** This is what lets the tray share the window's thread instead of needing one of its own: `request_repaint_after` keeps `update()` running with nothing on screen, so tray events are picked up. Measured at about **3 frames a second** against a 120 ms interval that asks for 8 — fine for a menu click, not something to build a timer on. Anything that must happen on a schedule belongs on the scheduler thread, not in a repaint interval.
- **`AppsUseLightTheme`, not `SystemUsesLightTheme`.** The first governs application chrome, the second the taskbar and Start menu, and a user can have them differ. Following the wrong one puts OmniToaster in light mode while every other app stays dark. The name also reads backwards from how it is spoken about: `1` means light.
- **An egui `Frame` is as wide as what is in it, not as wide as the row it sits under.** The Picture Library's "still in use" box stopped 36 points short of the Remove button above it, because its text wrapped before reaching the edge and the frame shrank to the text. `ui.set_min_width(ui.available_width())` as the first line inside the frame makes it span the pane, at every width.
- **A toast's text colour must come from the toast's background, never from the window's theme.** The background is the user's own colour and stays dark when the window goes Light, so taking `tokens.text` from the window's palette drew near-black text on a near-black toast — on the preview *and* the real toast, because both share one path, which is why nothing looked inconsistent. `Tokens::for_toast` picks the palette by the fill's luminance; `a_toasts_text_follows_its_own_background_not_the_window_theme` holds it.
- **A row that appears above a draggable widget mid-drag moves the widget under the pointer.** Dragging on the position map turns a preset into a custom point, which showed the Custom Point row — above the map, so the map jumped 78 points down while the button was still held and the toast moved far less than the hand. Anything a drag reveals goes *below* what is being dragged.
- **eframe's glow backend picks one OpenGL pixel format for every window, from the root viewport's options — and the driver may have no transparent one anyway.** A transparent toast viewport beside an opaque settings window logs "Cannot create transparent window: the GL config does not support it", and its unpainted corners come out black. Making the root transparent too only asks: the Intel Iris Xe driver here returned a format without transparency regardless (`WGL_TRANSPARENT_ARB` is an overlay-plane flag few drivers honour), and the corners stayed black. Cut the window to its shape with a window region instead (BUG-0007, ADR-015). When checking, `PrintWindow` captures the window's own pixels and ignores the region, so it shows black corners even when the screen does not: put a known window behind the toast and capture the screen.

## Localization and Fluent
- **A test that changes global state belongs in its own process, and on its own.** The active Fluent loader is process-wide, so a unit test that asserts English and a test that switches to Malay cannot share a process — one of them fails on thread scheduling, which is how a release went red here before. Switching tests live in `tests/switch.rs`, an integration test with its own process, and it is deliberately *one* test rather than several: `cargo test` runs the tests in one file in parallel threads, so two switching tests race each other just as surely.
- **Not everything on screen re-reads its strings.** An immediate-mode window does, so it follows a language switch for free. Anything set *once* does not: the window title is a viewport command, and the tray menu is built and handed to Windows. Both have to be told again, and the symptom is a window that is fully translated apart from its title bar.
- **Edit `locales/**/*.ftl` with the Edit tool, never a heredoc.** An unquoted heredoc expands `` `backticks` `` and `$name`, which turns `Remove { $name }?` into `Remove { }?` - a Fluent parse error that silently drops the whole message. The only symptom is a "locale … has N syntax errors" line in the log and a failing key-parity or bundle-parse test. Quote the heredoc (`<<'EOF'`) if you must script it, or better, write the script to a file.
- **A key added to one locale only** is caught by the key-parity test, not by the compiler, and only if the test names the missing keys on each side. A parity test that just asserts the counts are equal passes happily when each file is missing a different key. Add every new key to **both** `.ftl` files in the same commit.
- **`load_languages` takes the ACTIVE language first; fallbacks come after.** Passing `[en-US, ms-MY]` on the reasoning that "English first means English is the fallback" gets it exactly backwards: English becomes the active language and every lookup answers in English, while the UI still reports Malay — because the language *name* key reads "Bahasa Melayu" in both files and so proves nothing. Pass `[selected, en-US]`. The failure is invisible to a key-parity test and to any key whose two translations happen to match, so assert it on a key whose Malay genuinely differs, and against the loader the builder returns rather than the global one a `OnceLock` may already have claimed.
- **Fluent wraps every substituted value in U+2068/U+2069 isolating marks.** Correct for mixed-direction text; in two left-to-right languages they reach the user as stray boxes - `Logs are kept in ⁨D:\…⁩.` Strip them at the single place every substituted string passes through, not in each caller, because the next caller forgets.
- **The catalogue filename comes from the crate name unless you override it.** `fluent_language_loader!` and `fl!` both derive it from the calling crate, so a crate named `ot-i18n` looks for `ot-i18n.ftl` and reports "The language file … is not available" for a file that is plainly embedded and parses. `i18n.toml` has no setting for it; construct the loader with `FluentLanguageLoader::new("<domain>", fallback)`, accepting that `fl!` is then unavailable (ADR-006).

## Testing
- **A test that unwraps a process-wide `init()` is order-dependent, and "it passed locally" is not evidence.** `cargo test` runs a crate's tests in parallel threads in **one process**, so a global `OnceLock` or `tracing`'s global subscriber is claimed by exactly one test and every other call returns "already initialised". A test doing `init(..).expect(..)` therefore passes or fails on thread scheduling: `ot-i18n`'s formatter test passed twenty local runs and then failed the release job with `AlreadyInitialised`, taking a release down with it. Two tests had the same global, one tolerating failure and one unwrapping. Give such tests a shared helper that tolerates a sibling having initialised first **and asserts the resulting state** (so a test needing a different language fails loudly instead of silently reading the wrong bundle), or build a local instance instead of the global. Prove the fix with repeated runs *and* `--test-threads=1`, not one green run.
- **`egui_kittest` reports a widget's bounds in physical pixels, and the pane you compare them with is in points.** The first Appearance layout test compared them as they came and reported 123 overflows at 1.5x and 2x, every one of them the scale factor. Divide the accesskit `bounding_box()` by the scale first, and use it rather than `node.rect()`, which panics on a node with no bounds. And prove the detection can fail: a test that finds a 500-point button in a 300-point pane is what makes a green layout test mean something (`crates/ot-ui/tests/layout.rs`). The same holds for the pseudo-locale pass: assert the switch reached the strings, or it measures plain Malay twice.
- **Dropping a `tracing-appender` guard is not a flush you can rely on.** `WorkerGuard::drop` waits about 1.1 s for the background writer and then returns silently, so code that drops the guard and immediately reads the log file can find it empty when the writer thread is starved. The self-test did exactly that and failed 4 runs in 20 under above-normal-priority load (BUG-0006). Look for the line with a bounded wait instead, and reproduce a starvation flake with load at *raised* priority — Normal-priority busy loops on every core did not reproduce it at all.
- **A flaky test is a failure you have not localised yet.** It is tempting to re-run and move on when the second run is green. The first run was the honest one.
